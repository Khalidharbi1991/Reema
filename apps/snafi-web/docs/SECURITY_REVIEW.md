"Dormant" means the finding is in agy code, the `worker` user's setup or the `gemini_api` adapter only, none of which runs while `worker.yaml` names `claude_api`.

**My recommendation for this round:** safe to merge. The request is tool-free by construction: its top-level keys are checked against an exact set of six, and none of them can carry a tool, MCP server or container. Any reply block other than `text` (or ignored `thinking`), and any stop other than `end_turn` or `stop_sequence`, is rejected without a retry. Model output reaches tools only as proposals through `parse_reply` and the gate. The key goes only in the `x-api-key` header. It is checked for control characters when the brain is built, never appears in an error, `repr` or log, and is never resent on a redirect. The SDK is still forbidden. The daily limit counts every call before it is sent, retries and follow-ups included, under one lock shared by both lanes. The things Khalid should know: his Snafi chat now goes to Anthropic (SEC-65); the guard is a text scan that a REEMA file could get round by importing the brain module (SEC-62); the limit can lock Ahmad out wrongly in rare cases (SEC-63) and can be used up by a stolen session (SEC-64); and the Claude Console spend limit, which Khalid must set himself, is the only cap on a process that reads the key directly (SEC-51).

## This round: checked (Nov 13, the Claude API brain and the daily limit)

- **Tool-free request.** `build_request` builds a dict with exactly `model`, `max_tokens`, `system`, `messages`, `thinking` and `output_config`, and refuses to send if `set(body) != REQUEST_KEYS` (`claude_api.py:118`). Every message's `content` is a plain string, so no image, document, `tool_result` or `mcp_tool_use` block can be sent. `system` is a string. `output_config` holds only `effort` and a `json_schema` `format` with `additionalProperties: false`. There is no `tools`, `tool_choice`, `mcp_servers`, `container` or beta header, and the test checks for each of these. The Messages API does not run server tools that are not in the request, so the model cannot browse, run code or reach MCP. The model name goes in the body, not the URL, so worker.yaml cannot alter the endpoint.
- **Tool-shaped replies.** `extract_text` rejects any content block whose type is not `text`, `thinking` or `redacted_thinking`, including non-dict blocks and unknown future types, as "tried to use a tool", non-retryable. It then rejects every `stop_reason` other than `end_turn` and `stop_sequence`: `tool_use`, `pause_turn`, `refusal`, `max_tokens` and anything new, all non-retryable. Thinking text is never used. Only the text blocks go to `parse_reply`, which caps the reply at 4000 characters and 5 actions, drops tool names that do not match `^[a-z][a-z0-9_]{0,63}$`, and parses `args_json` as data. Every action then goes through `gate.decide` in `engine.chat_reply`. The follow-up after an approval ignores any actions. I found no path from model output to a tool except through the gate.
- **Key.** Read once from `Secrets` at build time, refused if it holds any character up to space or from DEL up (`_usable_key`), and sent only as `x-api-key`. The endpoint is a fixed https URL with no key. `__repr__` hides it. Every `BrainError` message is fixed text plus an HTTP status or exception type name. `run_job` stores `str(exc)[:300]` in the job row and the log, and none of those strings can hold the key or the response body. `http.client` errors that are not `OSError` (for example `BadStatusLine`) escape as "unexpected <TypeName>", with no text. Redirects are refused (SEC-16, fixed here). TLS uses urllib's default verified context. The key is not in any backup or in `brain_calls.json`.
