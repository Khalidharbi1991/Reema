# Snafi: security review of phases 1 and 2 (CSP and HSTS, sign-in throttle, fixed site URL, atomic chat send) (Agent 16)

Nov 13, 2026 · branch `fix/snafi-phase1-2` (commit 218beca "WIP ... (not reviewed)") compared with main · reviewer: Agent 16 (`reema-agent16-security`), under the Snafi scope Khalid approved for `apps/snafi-web/` and `src/snafi_worker/`.

This round covers four changes in the web app and the database. (1) Phase 2 fix: `send_chat()` (migration 0004, security invoker) saves a chat message and its `chat.reply` job in one transaction, and the composer submits by hand so a failed send keeps Khalid's text. (2) SEC-3: a per-request nonce Content-Security-Policy set in `src/proxy.ts`, and HSTS on every response in `next.config.ts`. (3) SEC-4: a sign-in throttle (5 wrong passwords in 15 minutes per email, and per client IP on Vercel), keyed by HMACs with `SNAFI_THROTTLE_SECRET`, stored in the hidden table `signin_failures` through two SECURITY DEFINER functions granted to `anon` and `authenticated` (migration 0005). (4) Redirects use a fixed site URL (`SNAFI_SITE_URL`, else Vercel's platform-set address, else the request origin on a development server only). The worker is not touched. Every earlier row is kept. Where this round changes an earlier row, the change is marked **Nov 13 (phases 1-2)**. This round adds SEC-70 to SEC-78.

**My recommendation for this round:** safe to merge. Before the **first Vercel deploy** (Khalid's yes needed for it), I recommend fixing SEC-70 (anyone holding the publishable key can fill the database through the new anonymous functions) and SEC-72 (parallel sign-in attempts get past the 5-try limit), and working through the deploy checklist in SEC-77. Neither is Critical or High, so Khalid decides. Answers to Ahmad's questions: **anon access to the throttle functions** cannot lock Khalid out (that needs the secret), but it does allow unbounded storage and CPU use (SEC-70); Khalid *can* be locked out through the sign-in form itself by anyone who knows his email (SEC-71). **Trusting `x-real-ip` on Vercel** is sound as long as Vercel is the outermost proxy and the code keeps the `VERCEL=1` condition; it stops being sound if another proxy (Cloudflare, for example) is put in front, and per-address IPv6 keys are cheap to rotate (SEC-71, SEC-72). **The CSP cannot be loosened by the request**: the proxy overwrites any client-sent CSP request header, and the policy text takes nothing from the request (SEC-3, closed). **`send_chat` grants** are right: execute for `authenticated` only, `anon` and `public` revoked, security invoker, so it adds no privilege (but SEC-18 is still open, and is now easy to close). **The `VERCEL_*` fallback** is safe: those values are set by the platform at build and run time, never by a request, and they are checked as https origins with no path; a production build without them fails closed with a 500. **First deploy:** see SEC-77.

## This round: checked (Nov 13, phases 1-2)

- **Atomic chat send.** `send_chat(uuid, text, text)` is `security invoker` with `search_path = ''`, refuses a null `auth.uid()`, and inserts the message and one `chat.reply` job with `jsonb_build_object('message_id', msg.id)`, so the job cannot point at another message. Because it is invoker, the existing column grants (`messages`: `conversation_id, role, body, lang`; `jobs`: `kind, payload, conversation_id`) and insert policies apply, and `user_id` comes from the column default `auth.uid()`; it adds no privilege and cannot write another user's rows. `RETURNING *` needs the `select` grant and the own-rows policy, which `authenticated` has. Execute is revoked from `public` and `anon` (needed on Supabase, which grants new functions to `anon` by default) and granted to `authenticated`; the test checks `anon` is refused. The plpgsql body is one transaction, and the test that revokes the job grant shows no message is left behind. `p_lang` and `p_body` are checked by the table's constraints and, before that, by `checkMessageBody` in the adapter. What is left is SEC-18. The composer change keeps the text on failure and hides the note on input; its pre-hydration gap is SEC-73. React escapes everything shown; no `dangerouslySetInnerHTML` was added.
- **CSP and HSTS (SEC-3):** see the SEC-3 row. The proxy sets the CSP on the request headers it passes on (so Next.js reads only the proxy's nonce) and on every response it returns, redirects and the 500 included. `proxy-session.ts` now builds its `NextResponse.next` from those same headers and copies refreshed cookies into them, so the nonce survives a session refresh. In a production build `'unsafe-eval'` is absent and `upgrade-insecure-requests` is present. What is left is SEC-76.
- **Throttle (SEC-4):** see the SEC-4 row. The keys use a 32+ character server-only secret; a development server uses a per-process random secret, never a fixed one. `VERCEL` is a platform setting, not a request header, so a client cannot turn the IP key on or off. `x-real-ip` is accepted only as hex, dots and colons, up to 64 characters, so it cannot carry anything but an address.
