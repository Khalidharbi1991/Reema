"Dormant" means the finding is in agy code or the `worker` user's setup only, which does not run while `worker.yaml` names `gemini_api`.

**My recommendation:** safe to merge as Khalid's informed choice, once the PowerShell hook is confirmed. The deploy and task scripts do what the docs say, with small gaps (SEC-54, SEC-55, SEC-36). The real change is that **Windows no longer separates Snafi's keys from anything else that runs as Khalid** (SEC-51). That includes Claude Code sessions, the agents' scripts and tests, packages that Development agents install, Blender scripts, and whatever else Khalid runs. All of them can now read the Supabase secret key, the Gemini key and the backup signing key from Credential Manager, read or attach to the worker's memory, read the backups and logs, and write the worker's pause file. Only Claude Code's deny rules and the guard stand in the way, and they match names in commands. They cannot see inside a script a session writes and then runs. The docs say this honestly. With the Gemini brain this is Medium. The brain cannot reach the keys, and an attacker who can already run code as Khalid can reach most of his accounts anyway. **Before step 3** (Gmail and Calendar tokens, and real sends), Khalid should re-decide this. My advice is to run the `gemini_api` worker as a separate non-admin user again, because the Supabase secret key lets anyone write an "approved" card that the worker will then run. Before go-live, do the clean-up steps in SEC-52 and SEC-43. In particular, **do not press Enter at the `set-secrets` questions**, because that keeps the old Nov 9 copies under Khalid's user.
