**My recommendation:** the rename is safe. Nothing that runs depends on the old name. The deploy, the task script and the launcher use only the `$WorkerUser` default, which is now `worker`. The worker's code finds its folders through `USERPROFILE`, `APPDATA` and `LOCALAPPDATA`, not through the account name. The Credential Manager target names are unchanged. The ACLs the first deploy wrote (the `C:\SnafiWorker` lock, the denies on `D:\Projects` and `D:\Antigravity_Projects`, and the backups grant) are stored by SID, so `Rename-LocalUser` carries them over. The first sign-in after the rename will make the profile `C:\Users\worker` (or `C:\Users\worker.<PC>` if that folder already exists; the guard pattern covers both). Order: rename first, then re-deploy, then (re-)register the task, then sign in as `worker`. A re-deploy is not required for the ACLs, but it is safe and I recommend it (SEC-43). The generic name does not weaken the admin check against the local account. Two things are worth making stronger, because "worker" is a name that a domain or Microsoft Entra account could also have: compare by SID instead of by name, and give icacls the SID (SEC-42). The generic name is also easier to guess, which adds weight to SEC-31 (deny network and RDP logon). SEC-27 is still the main design risk. **It should be treated as High, and fixed, before step 3 puts email or any other outside content in front of agy.**

## This round: checked, no finding

- **Nothing that runs still points at the old name.** The deploy, task, launcher and `snafi.py` use only `$WorkerUser`, whose default is now `worker` in both scripts. `snafi.cmd` uses `%~dp0` paths. The worker code finds agy and its data through `LOCALAPPDATA`, `APPDATA`, `USERPROFILE` and `Path.home()` (`agy.py:87-89,278`, `config.py:26-29`), not through the account name. `%APPDATA%\REEMA\snafi-worker` is a folder inside the account's own profile, so the folder name does not have to match the account. Credential targets (`REEMA-Snafi:<NAME>`) do not include the account name. The task name "Snafi Worker" is unchanged.
- **The profile.** The account has never signed in, so the first sign-in after the rename makes `C:\Users\worker`. If a folder of that name already exists, Windows uses `C:\Users\worker.<PC>`. The guard pattern `users/(snafi-)?worker(/|\b)` matches both, as well as the old `C:\Users\snafi-worker`. `worker` is 6 letters, so it has no separate 8.3 short name (unlike `snafi-worker`, which had `SNAFI-~1`).
- **The guard's patterns.** `users/(snafi-)?worker(/|\b)` does not match `users/workers` or `users/coworker`, so it does not cover more user folders than it should in a way that matters. `(snafi-)?worker[^\s]*/(appdata|\.gemini)` is now broader (any path with "worker" in it, for example `src/snafi_worker/.../appdata`). That can only block more, not less. `\brunas\b` is unchanged. Gaps for wildcards and names built from pieces are noted in SEC-25.
- **Name collisions.** If another local account called `worker` already existed, `Rename-LocalUser` would refuse, so the rename cannot merge two accounts. The admin check's name match is exact after the backslash (SEC-42 for what it does not cover).
- **Secrets, logs and the brain:** nothing new is logged, printed or sent. Only message strings and docstrings changed in the worker code. No change to the gate, honesty check, backup, restore or the brain's text-only request.
- **Packages:** none added or changed.
- **Web app:** not touched by this diff. Only the publishable key is used, as before.
