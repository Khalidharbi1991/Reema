## Step 2: checked, no finding

- **Migration 0002 (RLS and grants):** RLS is enabled **and forced** on all six new tables, with select-own policies only. `revoke all` from `anon` and `authenticated` comes before `grant select`, which also cancels Supabase's default privileges on new tables. The app's job insert is limited to the columns `kind`, `payload` and `conversation_id`, and the policy pins `kind = 'chat.reply'`, `lane = 'chat'` and `attempts = 0` (the new columns default to that and are not insertable). `user_id` still defaults to `auth.uid()`. The new `messages` columns (`approval_id`, `meta`) are not insertable by the app, and a test covers this. There are no update or delete grants.
- **Definer functions:** `decide_approval` and `request_undo` are `security definer` with `search_path = ''`. Every name is schema-qualified. They refuse a null `auth.uid()`, change one row matched on `id`, `user_id = auth.uid()` and the expected state, and queue the follow-up job with the server-set `user_id` and the card's own `conversation_id`. Execute is revoked from `public` and `anon` (which cancels Supabase's default function grants) and granted to `authenticated`. `claim_job` is `security invoker`, granted to `service_role` only, and uses `FOR UPDATE SKIP LOCKED`. If the role that owns the functions in Supabase does not bypass RLS, the functions fail closed ("no pending approval"), not open.
- **Only the app can approve:** `approval.resume` and `action.undo` jobs can come only from the two definer functions. The worker re-reads the card or log entry, scoped by the job's `user_id`, checks its state and **re-runs the gate** on the stored tool and args. The app cannot change `args`. The brain's claimed level is ignored. Unknown tools and Level 4 names (exact names plus keyword match) are refused. Arguments are type- and length-checked.
- **Cross-user isolation in the worker:** every select and write in the engine and tools carries the job's `user_id`, which the database sets from `auth.uid()` for app jobs. `chat_reply` and `apologise` check that the message belongs to the job's user. A test covers "another user's message is never answered".
- **Gemini adapter:** the request body is checked to have exactly `systemInstruction`, `contents` and `generationConfig`, and only text parts. Any non-text response part (`functionCall`, `executableCode`, …) is rejected and not retried. The key goes only in the `x-goog-api-key` header, and the `repr` hides it. Error messages carry only the HTTP status, never the body. The URL is fixed `https`. The model name comes from the repo's `worker.yaml`.
- **Supabase adapter:** the URL must be `https`. The publishable key is refused. The key goes only in headers. Table and column names are regex-checked, and filter values are URL-encoded into `eq.` filters, so I found no way to inject PostgREST operators or extra parameters. Error text holds the PostgREST message, cut to 200 characters, with no key.
- **Secrets handling:** `Secrets` hides its values in `repr` and `str` and in parse errors, and `--check` prints names only. The logs hold job ids, kinds, statuses, fixed error strings and exception type names, with no message text and no keys. One exception: a PostgREST error message can quote a bad input value from a job payload. That is a minor point, not personal data in practice.
- **Restore SQL:** table names come from a fixed list, column names are regex-checked, strings are single-quoted with `'` doubled (safe with `standard_conforming_strings` on, the default), JSON is cast `::jsonb`, NUL bytes are refused, and booleans and numbers are written as literals. I found no injection. `--to-database` refuses non-empty targets.
- **Backup pruning** deletes only files matching `^snafi-backup-\d{8}-\d{4}\.json\.gz$` in the configured folder, only after a successful write. The temporary `.part` file is written and then moved into place with `os.replace`.
- **Task Scheduler script:** it runs as the current user, Interactive, `RunLevel Limited`, with no stored password and `MultipleInstances IgnoreNew`; Khalid runs it himself. `-ExecutionPolicy Bypass` applies only to that one invocation. See SEC-19 for the module path.
- **Web app:** server actions validate the decision value and UUIDs (`checkId`), and wrap failures without leaking error text to the client. There is no open redirect, no new cookie, and no `dangerouslySetInnerHTML`. The service worker and `public/` are not in this diff. Preview mode still needs `NODE_ENV=development` and no keys, and its in-memory mailbox is module-local. Only the publishable key reaches `createServerClient` (`adapters.test.ts` still fails the build if `SERVICE_ROLE` or `SUPABASE_SECRET` appears in `src/` outside `env.ts`).
- **Packages:** one new web package, `adhan` 4.4.6, pinned exactly and approved by Khalid. It computes prayer times locally and makes no network call in the code shown. The Hijri date uses the built-in `Intl` Umm al-Qura calendar. The worker adds no Python package; it uses the standard library plus PyYAML (`yaml.safe_load`), which REEMA already uses. I could not check that `adhan` 4.4.6 exists or has no advisories (no network, and the lock file was left out).
- **Network calls:** the worker calls only the Supabase URL from `worker.env` and Google's Generative Language endpoint, both approved by the PRD. The web app adds no outside call; prayer times are offline.
- **No `eval`, `exec`, `pickle`, `subprocess` or `shell=True`** in the worker. The only subprocess call is in a test (`restore.test.ts`), which uses `execFileSync` with an argument array and `python -I`.
