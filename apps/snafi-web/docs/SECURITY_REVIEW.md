It now accepts any printable ASCII without spaces, 20 to 512 characters, and refuses with a specific reason (control character from a failed Ctrl+V paste, space, non-English character, length) without showing the key. Tests were added in `tests/test_snafi_worker_secrets.py`. Khalid's key was refused three times; he asked to bypass the check, and this loosens it instead. "Dormant" means the finding is in agy code or the `worker` user's setup only, which does not run while `worker.yaml` names `gemini_api`.

**My recommendation for this round:** safe to merge. No accepted value can inject a header: CR, LF, tab, every other control character and DEL are refused before storing, so the value that reaches `x-goog-api-key` is 20 to 512 characters from `!` to `~`, all legal in an HTTP header value. Python's `http.client` would also refuse CR or LF in a header value on its own. No refusal message contains any part of the key; the length shown on a length failure is acceptable (SEC-60). The one real gap is that the looser check now also accepts the legacy Supabase `service_role` JWT (it contains dots), and the old check already accepted an `sb_secret_...` key. A wrong paste at the Gemini question would store the Supabase secret key as the Gemini key, and the worker would send it to Google on every chat (SEC-58). That is Low: it needs a mistake by Khalid, and Google would only reject it, but the key would leave this PC. Khalid's Ctrl+V refusal is most likely the control-character case (`getpass` on Windows reads Ctrl+V as the character `\x16`), and the new message tells him to paste with a right-click.

## This round: checked (Nov 13, the Gemini key check)

- **Header injection.** The checks run on the value after `strip()`. Anything below code 32 or equal to 127 is refused first, so CR, LF, tab, NUL and the `\x16` that a Ctrl+V in `getpass` produces cannot be stored. Then spaces, then anything outside ASCII. What is accepted is 20 to 512 characters from `!` to `~`. Every one of them is a legal HTTP header value character (RFC 9110 `field-vchar`), and `http.client` sends them as Latin-1 unchanged. Characters such as `:`, `;`, `,` and `"` are harmless inside a header value. There is no way to add a second header or split the request. The key goes only in the header, never in the URL (`ENDPOINT` uses only the model name).
- **No key material in any message.** None of the four refusal messages contains the value or any part of it. `ask()` prints only `not stored: {exc}` and `stored {name}`. The new test checks that the refused value does not appear in the message. The length on a length failure is SEC-60.
- **Edge cases.** An empty paste gives "it is 0 characters long", unless a value is stored and Enter keeps it (SEC-48 and SEC-52 still apply). The order of the checks means a short value with a control character gets the paste message, which is the more useful one. `str.isspace()` after the control-character check can only catch the plain space.
- **What is newly accepted.** Dots, colons, slashes and other punctuation, so newer Google key formats pass (the test uses an `AQ.` example). Of the other Snafi values, the legacy Supabase JWT and the Supabase project URL are newly accepted (SEC-58). An `sb_secret_` key and the owner UID (36 characters, hyphens) were already accepted by the old rule.
- **Upper bound.** 512 characters in one header is far below any limit in `http.client` or Google's front end, so a long value does no harm beyond a refused call.
- **Packages:** none. **Network:** no new call. **Web app:** not touched; only the publishable key is used, as before. **Logs:** the diff adds no logging.
