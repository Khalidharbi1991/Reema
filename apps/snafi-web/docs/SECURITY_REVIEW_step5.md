What step 5 gets right, from the code I read (not verified by running anything):
- **SSRF.** The three push-host rules agree character for character: the database's `push_endpoint_ok`, the app's `PUSH_ENDPOINT` and the worker's `ENDPOINT`. Each is anchored with `^` and `$` (JS without `m`; a Postgres ARE, which is not newline-sensitive by default) or `\Z` (Python). The host comes from a fixed list of five forms, followed by a literal `/`, so a user, port, backslash, space or newline cannot get in, and `@` or `:` after the first `/` stay in the path. The length is 20-1000 in all three. The worker re-checks before every post (`send` → `endpoint_ok`), reads only the owner's subscriptions, posts with an opener that refuses redirects (a 3xx counts as a failure and is never followed), and sets a 10-second timeout. The VAPID `aud` is built from the checked endpoint's netloc, so the signed token is only good for that push service.
- **Nothing private in the push.** `payload()` takes only a known kind, `en` or `ar`, and a UUID. Anything else raises. The service worker ignores everything in the push except those three fields, shows fixed text per kind (unknown kinds get the generic "update" text), uses the UUID only as a tag, and opens the fixed path `/today` on a tap (no URL from the push, so no open redirect). So the lock screen, Apple, Google, Mozilla and Microsoft see no title, sender, subject or reminder text. What they can still see is metadata (SEC-124).
- **Never twice.** `insert_once` is PostgREST `on_conflict=user_id,dedupe_key` with `resolution=ignore-duplicates`, backed by the table's UNIQUE. The claim `new/held → delivering` is a conditional PATCH. Reminders set `fired_at` with an `is.null` condition before anything else. A retried `push.test` job reuses `test:<job id>`. So retries, two threads and crashes cannot send the same thing twice. The cost is the other way round: a message can be lost (SEC-121), and a restore can repeat some (SEC-122).
- **Quiet time and cap** are enforced in `Notifier`. Every message passes through `_release`, which holds it while `quiet_until` says it is quiet, and checks the cap at the moment of release. The cap counts only rows that were pushed and count towards the cap, by Jeddah day. Reminders and the test push do not count, as Khalid asked. `daily_cap` is checked to 1-50 in the database, in the RPC, in the app and again in the worker.
- **Migration 0008.** RLS is enabled and forced on all four tables. `anon` and `authenticated` lose every privilege, then get back only `select` on `user_settings` and `cards`, each with an own-row policy. `push_subscriptions` and `notifications` have no app policy at all. Each of the five RPCs is `security definer` with `set search_path = ''`, uses qualified names, takes the user from `auth.uid()` (it refuses null), never from an argument, and is granted to `authenticated` only. `remove_push_subscription` and `dismiss_card` touch only the caller's rows. `request_test_push` inserts only `push.test` jobs for the caller, at most one waiting, and the app's own jobs insert policy is unchanged (the test checks it). The worker runs a test push only for the owner.
- **VAPID key.** It is made at random by `set-secrets`, stored only in Credential Manager, and never printed (`--status` shows names only; `--push-key` prints only the public half). `PushSender` has a hidden `repr`, and no log line carries it. Only the public half reaches Vercel (`NEXT_PUBLIC_SNAFI_VAPID_PUBLIC_KEY`, checked as 87 base64url characters starting with `B`). The web app still uses only the publishable key and the user's session.
- **Logs** get kinds, statuses, counts, HTTP status codes and exception type names, never text. **No brain call** anywhere in `proactive/`. **No new package**: `cryptography` was already locked. The phone's key is checked to be on the curve before ECDH.
- **Settings server actions** each call `requireSession()`, coerce every field (`=== true`, `String`, `Number`), and pass through `checkSettings` and `checkPushKeys`, then the RPC's own checks. The language comes from the app's own preference. A failure returns only `{ok: false}`.
- **Today cards** are rendered as React text (`dir="auto"`, `whitespace-pre-line`), with no HTML.

## Answers to the points Ahmad named

1. **SSRF through push endpoints:** none found. The DB, TS and Python rules agree (same host list, same path character class, same length bounds, anchored at both ends), the worker re-checks at send time, posts only to the owner's rows, and never follows a redirect. The tests feed the same 11 or 12 addresses to all three. Left: urllib's default proxy handling (SEC-68 note).
2. **Private data reaching the payload, the lock screen, logs or the push services:** not the content. The payload has three fields, all checked; the service worker shows fixed text; logs carry no text. The push services still learn which *kind* of message it is, from the ciphertext's length and the `Urgency: high` header on reminders, plus timing, counts, the PC's IP address and the Snafi site address (SEC-124, Info). Private content does go to Supabase and the backups, which is new data to keep (SEC-127).
3. **Never twice under retries, crashes and the two-step claim:** holds within one database (see the summary). It does not hold across a restore (SEC-122). The two-step design makes delivery "at most once", so a failure at the wrong moment loses a message without a word (SEC-121). The "never repeat" rule can also swallow a real reminder (SEC-119).
4. **Daily cap and quiet time:** correct as built. Quiet windows are computed for yesterday, today and tomorrow, and a message is held until the window ends and then rechecked. The cap is checked at release time. Small points are in SEC-129 (the 500-row scan; no cap on reminders, which SEC-120 makes matter).
5. **The new RPCs:** sound (definer, `search_path = ''`, `auth.uid()`, granted to `authenticated` only). One user cannot take over another's endpoint, except in a narrow race (SEC-126, Info). The 5-subscription limit keeps the five newest per user. `request_test_push` is limited to one waiting job, and the worker refuses non-owner jobs.
6. **VAPID key handling:** never printed or logged, and only the public half leaves. A damaged stored value stops the worker from starting instead of only switching push off (SEC-123, Low). The guard was not updated for the new names (SEC-128, Info). The impact of a leak is small, because the service worker shows only fixed text.
7. **Reading Yahoo's Sent folder headers:** read-only (`EXAMINE`, `BODY.PEEK[HEADER.FIELDS (TO CC BCC)]`), at most 500 emails from the last 90 days, kept only in the worker's memory for 6 hours, and never logged, stored, sent to Supabase or sent to the brain. It is what Khalid asked for, so no decision is needed, but Ahmad should tell him in plain words that the worker now reads the recipient lists (not the bodies) of his Yahoo sent mail. One weakness to tell him: the rule trusts the From header, which a stranger can forge (SEC-125, Low).
8. **Restore neutralisation:** waiting notifications become `cancelled`, as intended. But reminders that fired after the backup, and every past reminder in a pre-step-5 backup, will go off again (SEC-122, Low).
9. **Settings form server actions:** sound (session, coercion, double checks, own-row RPCs). A UX point is in SEC-129.
