## Summary

**Open Critical 0, open High 0. Nothing in this round blocks merging `feat/snafi-memory-family` to main.** Khalid decides.

**For Khalid to decide:**
- **Medium (3):** SEC-199 (the no-secrets rule is easy to pass by accident: common Arabic wording such as «كلمة سر» and «باسورد», phone and card numbers written with brackets or slashes, other digit forms and invisible characters), SEC-200 (outside content can still reach memory one message later, through Ahmad's own earlier reply), SEC-201 (Forget leaves memory text in the action log: memory searches, the family list, "already saved" entries, Undo'd saves and the facts the migration deleted).
- **Low (5):** SEC-202 (`MAX_ACTIONS` 8 applies to every tool, not only memory), SEC-203 (restoring a backup brings forgotten items back), SEC-204 (old facts that break the rule stay and still reach the brain), SEC-205 (the worker's memory delete has no owner filter; no database link between a date's owner and its person's owner), SEC-206 (memory now goes into the follow-up call with untrusted content, where a Level 2 draft can be made).
- **Info (7):** SEC-207 to SEC-213 (checks recorded and small notes).

**Answers to Ahmad's points, in short:**

1. **Migration 0010: sound as access control.** `family_members`, `family_dates` and `interview_state` have RLS enabled and forced, one select-own policy each, all rights revoked from `anon` and `authenticated` and only `select` granted back; the app has no direct write on them or on `facts` (the test says so; I did not run it). The six save and forget functions are `security definer`, `search_path = ''`, take the user only from `auth.uid()` and refuse null, touch only `where ... user_id = uid`, check that a date's person is the caller's own, revoke from `public, anon` and grant to `authenticated`. `snafi_scrub_log` is revoked from `public, anon, authenticated` and scrubs only `where user_id = p_user`. The no-secrets rule is a CHECK on every new or changed row for every writer, `service_role` included, and `NOT VALID` only for facts already there (SEC-204). "Forget really deletes" holds for the row itself and for the log entry that saved it, but not for every copy in the log (SEC-201). The guard's wording and separator coverage is thin (SEC-199).
2. **Migration 0011: sound.** `remove_all_push_subscriptions()` is definer with `search_path = ''`, refuses no user, deletes only the caller's addresses, upserts only the caller's `user_settings` with push off, returns a count, is revoked from `public, anon` and granted to `authenticated`. The Settings form asks first, cancels this phone's own subscription, and falls back to the account switch only when the function is missing (PostgREST "no such function" codes); any other failure is shown, not hidden (SEC-212).
3. **Worker:** memory reaches the brain only inside `<data source="memory">`, built by `data_block` (data tags neutralised); never as a turn or in the system prompt (checked; the test asserts it). Memory writes are refused in the follow-up after outside content (checked), but not in the next message (SEC-200). At most 3 saves a message, 6 in the interview, counted in code on the job (checked; the app cannot set the job's `_interview` or `_memory_writes` keys, it inserts only `kind` and `payload`). Saves are Level 2 with Undo that hard-deletes (checked; the log entry keeps the text, SEC-201). There is no forget tool for the brain (checked: `MEMORY_TOOLS` has none, and Undo is only Khalid's own `action.undo` job). Interview commands are matched in code on the normalised whole message with no brain call (checked). Family reminders are kind `reminder`, never twice (`family:<date id>:<day>:week|day`), never counted to the cap, through `Notifier.deliver` (so prayer quiet applies), and the lock screen shows the fixed reminder text from `sw.js` (checked). The gift-ideas job checks the owner, is queued once per date and day, gives the brain relation, age, note and up to 10 family facts as a data block, uses only the reply text (any actions ignored), cuts to 3 lines of 120 characters, and counts toward the daily brain limit (checked; SEC-209). The invite goes out once (checked). Backup schema 7 holds the three new tables and still never `cards` or `notifications` (checked). Restore drops soft-deleted facts and facts that fail the guard (checked), but brings back forgotten items (SEC-203).
4. **Web app:** no XSS (every memory text is drawn as React text; no `dangerouslySetInnerHTML`, no link from memory text); no redirect from input (`router.push("/chat")` is fixed); every server action calls `requireSession()` first and returns only an error kind, never the database message; ids are checked as UUIDs, sections, relations, labels and dates are checked before the database checks them again; the Supabase adapter is `server-only` and uses the signed-in session with the publishable key only; the in-memory adapter is refused in a production build; `startInterview` sends only the fixed phrase from the message table. The service worker is unchanged and never caches pages, so the About me page is never stored on the phone (SEC-211).
5. **Family members (later):** every new table is select-own under forced RLS, every function acts only on `auth.uid()`'s rows, the About me page reads through RLS, and the worker reads memory by the job's own `user_id` (chat) or the owner's id (scheduler, gift ideas, invite). Another signed-in user cannot read or change Khalid's memory by any path I found. Two defence-in-depth gaps in SEC-205.
