What step 4 gets right, from the code I read (not verified by running anything):
- **IMAP injection:** every search value is sent as a quoted string, with `\` and `"` escaped and every control character refused (`_quote`), or as a counted UTF-8 literal. UIDs are digits from the server, and ids must match `y<digits>_<digits>`. The folder names are fixed or come from the server's LIST, and they are quoted too.
- **Header injection:** subjects pass `CONTROL` (SEC-82). Addresses pass `EMAIL`. In-Reply-To and References from the replied-to email must match `<[^<>\s]{1,250}>`. `EmailMessage` refuses line breaks inside a value. Bcc goes on the envelope only.
- **Reading never marks mail read:** the Inbox is opened read-only (EXAMINE), and every fetch is `BODY.PEEK`. Only Drafts is ever opened read-write, and only to delete a draft.
- **Draft Undo deletes only that one draft:** the id must match `yd<validity>_<uid>`, the account and id prefix must agree, and Drafts' UIDVALIDITY must still match. The UID must exist, and the server must offer UIDPLUS. The delete is `UID STORE +FLAGS.SILENT (\Deleted)` followed by `UID EXPUNGE <that uid>`, so it never runs a plain EXPUNGE.
- **TLS and hosts:** `IMAP4_SSL` to `imap.mail.yahoo.com:993` and `SMTP_SSL` to `smtp.mail.yahoo.com:465`, both with `ssl.create_default_context()` (certificate and host name checked). The hosts are fixed in code, not taken from `worker.yaml`. Todoist accepts only `https://api.todoist.com` with no user and no port, refuses redirects, and sends the token only in the Authorization header.
- **Account routing:** the gate decides the account from the id (a reply goes from the account the email came from) and refuses a mismatch. `prepare` puts `account` and `from_address` into the card args, so the args hash binds them. The summary reads "Send from Yahoo (address) to …". At run time the send is refused if the Yahoo address changed after Approve.
- **An email or task cannot trigger a send or delete:** sends and deletes are Level 3 cards only, and the proof tests are repeated for Yahoo and for a task. What an email or task *can* still trigger is Level 2 (SEC-105).
- **Secrets:** no secret reaches the brain, a log line, Supabase or the repo. The adapters and `StoredLogin` have hidden `repr`s, and the error messages are fixed strings raised `from None`. The Today feed logs only the three statuses. No new package is added (standard library only), and the web app gets no new key.
- **`today_feed`:** RLS and grants unchanged in effect (select own row; only `service_role` writes). There are size and shape checks on `emails` (10) and `tasks` (10), and status checks on both new columns. React renders every field as text.

## Answers to the points Ahmad named

1. **IMAP command injection:** none found. Search words become quoted strings (control characters refused, `\` and `"` escaped) or one counted UTF-8 literal; any further non-ASCII words are matched locally. Keys come from a fixed list, dates are built by code, UIDs are digits, and folder names are quoted (`yahoo/mail.py:61-65,165-203`).
2. **Header injection in drafts and sends:** none found. Subject passes `CONTROL`, addresses pass `EMAIL` (see SEC-112 for `$`), reply headers have a strict pattern, `EmailMessage` refuses line breaks inside a value, and Bcc goes on the envelope only (`:397-410,466-497`).
3. **Reading never marks mail read:** yes. EXAMINE (`readonly=True`) for the Inbox, `BODY.PEEK` for every fetch, and the Today feed fetches headers only.
4. **Draft Undo deletes only that draft:** yes, and only with UIDPLUS (`UID STORE` then `UID EXPUNGE <uid>`), after checking the account, the id form, UIDVALIDITY and that the UID exists (`:447-463`; `personal_tools._undo_google`).
5. **TLS and fixed hosts:** yes, for IMAP, SMTP and Todoist. Todoist refuses redirects and sends the token only in the header (SEC-16 note). The proxy point is SEC-68.
6. **Sending from a different account than the card shows:** not possible as far as I can see. The account and `from_address` are in the hashed card args, the gate re-checks the account against `in_reply_to` on resume, the run uses exactly the card's args, and the address is compared again before the send.
7. **Honesty account rule:** works for the forms it knows; gaps in SEC-109.
8. **New data in logs, Supabase or the brain:** no secrets anywhere, and no new log content (statuses and fixed messages only). Supabase, backups and the brain get Yahoo bodies, task text and Khalid's Yahoo address, as described in SEC-110, SEC-113 and the SEC-65 note.
9. **`today_feed` columns and RLS:** sound (select own row; only `service_role` writes; shape, size and status checks). The availability point is SEC-107.
10. **The guard and the new secrets and hosts:** covered (SEC-114). The secrets' real exposure is SEC-51, reopened.
