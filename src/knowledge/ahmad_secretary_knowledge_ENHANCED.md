**Communication Priority Levels:**
- **P1 - Critical**: System failure, blocked delivery, owner directive
  - Response: Within 1 hour
  - Escalation: Immediate to Khalid if unresolved in 2 hours
  - Notification: All relevant agents alerted
  - Documentation: Incident report within 24 hours

- **P2 - High**: Quality gate failure, deadline risk, resource conflict
  - Response: Within 4 hours
  - Escalation: To Khalid if unresolved in 8 hours
  - Notification: Abdullah and affected agents
  - Documentation: Issue log entry

- **P3 - Medium**: Status updates, process questions, minor issues
  - Response: Within 24 hours
  - Escalation: To Abdullah if unresolved in 48 hours
  - Notification: Relevant agent only
  - Documentation: Tracked in daily status

- **P4 - Low**: Suggestions, improvements, FYI items
  - Response: Within 48 hours
  - Escalation: Included in weekly review
  - Notification: None (batch in status report)
  - Documentation: Improvement backlog

### 1.2 Communication Quality Standards

**Message Clarity Framework (CLEAR Protocol):**
- **C**oncise: Maximum 3 key points per message
- **L**ogical: Structured with context → issue → action needed
- **E**vidence-based: Facts and data, not opinions
- **A**ctionable: Clear next steps with owners and deadlines
- **R**ecorded: Documented for traceability

**Writing Standards for Different Audiences:**

| Audience | Tone | Detail Level | Format | Language |

| External Partners | Formal business | Contractual detail | Business correspondence | EN or AR |

**Tone Guidelines:**
- Internal (team): Professional, supportive, solution-oriented
- Internal (Khalid): Respectful, concise, decision-focused
- External (clients): Polished, confident, service-oriented
- External (partners): Formal, precise, contractual awareness

## 2. PROJECT COORDINATION & WORKFLOW MANAGEMENT

### 2.1 SOP Generation Workflow - Detailed

**Standard Workflow (12-24 day process):**
```
Phase 1: INITIATION (Day 1)
  Owner Input:
    Khalid → Ahmad: Process request + priority + client context
  Secretary Actions:
    Ahmad → Create project tracking entry (ID, dates, assignments)
    Ahmad → Verify requirements completeness (checklist)
    Ahmad → Identify applicable standards (cross-ref standards_mapping.yaml)
    Ahmad → Brief Abdullah on requirements + constraints + timeline
    Ahmad → Notify Khalid of project acceptance + planned timeline
  Quality Gate: Requirements complete and clear ✓

Phase 2: RESEARCH & STANDARDS (Days 2-5)
  Parallel Workstreams:
    Stream A: Abdullah → Taif (Research)
      - ITIL/ITOM research for process
      - Industry best practices
      - ITOM.pdf reference extraction
      - ITOM alignment (if applicable)
    Stream B: Abdullah → Mohammad (Standards)
      - Applicable standards identification
      - Compliance requirements mapping
      - Regulatory obligations
      - Control framework alignment
    Stream C: Abdullah → Layla (Data/BI)
      - KPI framework design
      - Dashboard template selection
      - Data model planning
      - Visualization strategy
  Secretary Actions:
    Ahmad → Track parallel progress daily
    Ahmad → Identify cross-dependencies
    Ahmad → Update Khalid if timeline risk detected
  Quality Gate: Research complete, standards mapped, analytics planned ✓

Phase 3: CONTENT CREATION (Days 6-12)
  Sequential + Parallel:
    Abdullah → Saad (Content):
      Input: Research findings + standards requirements + analytics framework
      Output: 15-30 page SOP document
      - All 11 template sections
      - RACI matrix
      - Process flow diagrams
      - Decision trees
      - Compliance mapping tables
    Parallel: Layla refines analytics framework based on SOP content
  Secretary Actions:
    Ahmad → Monitor daily progress against milestones
    Ahmad → Coordinate if Saad needs additional input from Taif/Mohammad
    Ahmad → Track page count and section completion
  Quality Gate: Draft complete, all sections populated ✓

Phase 4: QUALITY REVIEW (Days 13-16)
  Abdullah → Faisal (Review):
    - Quality scoring (target >= 85/100)
    - Technical accuracy validation
    - Standards compliance verification
    - Completeness assessment
    - Consistency checking
  IF score < 85%:
    → Return to Saad with specific feedback
    → Targeted revisions (not full rewrite)
    → Re-review by Faisal
    → Maximum 2 revision cycles
  IF score >= 85%:
    → Proceed to formatting
  Secretary Actions:
    Ahmad → Track quality scores and trends
    Ahmad → Escalate if 2+ rejection cycles
    Ahmad → Report quality metrics to Khalid
  Quality Gate: Score >= 85%, all critical issues resolved ✓

Phase 5: FORMATTING (Days 17-19)
  Abdullah → Bee (Format):
    - PDF generation (PDF/UA compliant)
    - DOCX generation (accessible)
    - HTML generation (WCAG 2.1 AA)
    - Markdown generation
    - Accessibility validation
    - RTL support for Arabic (if bilingual)
  Secretary Actions:
    Ahmad → Verify all requested formats generated
    Ahmad → Spot-check formatting quality
    Ahmad → Package deliverables
  Quality Gate: All formats generated, accessibility validated ✓

Phase 6: APPROVAL & DELIVERY (Days 20-24)
  Secretary Actions:
    Ahmad → Compile delivery package
    Ahmad → Prepare executive summary for Khalid
    Ahmad → Submit for Khalid's final approval
    Ahmad → Upon approval: deliver to client
    Ahmad → Send delivery confirmation with feedback form
    Ahmad → Archive all project records
    Ahmad → Update project metrics
    Ahmad → Schedule post-delivery follow-up
  Quality Gate: Owner approved, client accepted ✓
```

### 2.3 Dependency Management

**Agent Dependencies (Detailed):**
```
PHASE 2 (Parallel):
  Taif (Research) ──────────────→ Saad (Content)
  Mohammad (Standards) ──────────→ Saad (Content)
  Layla (Data) ──────────────────→ Saad (Content)
                                     ↓
PHASE 3 (Sequential):
  Saad (Content) ──────────────→ Faisal (Review)
                                     ↓
PHASE 4 (Conditional):
  Faisal (Review) ──[PASS]──→ Bee (Format)
  Faisal (Review) ──[FAIL]──→ Saad (Content) [revision loop]
                                     ↓
PHASE 5 (Sequential):
  Bee (Format) ──────────────→ Ahmad (Delivery)
                                     ↓
PHASE 6 (Approval):
  Ahmad (Delivery) ──────────→ Khalid (Approval)
  Khalid (Approval) ──[OK]──→ Ahmad (Client Delivery)
  Khalid (Approval) ──[REJ]──→ Ahmad (Coordinate Revisions)
```

**Critical Path Analysis:**
The critical path for a standard SOP is:
```
Initiation → Research → Content → Review → Format → Delivery
   1 day    + 3 days  + 6 days + 3 days + 2 days + 3 days = 18 days
```
Parallel activities (Standards, Data/BI) run alongside but do not extend the critical path unless they are delayed beyond the research phase.

**Dependency Risk Indicators:**
| Risk | Signal | Impact | Mitigation |
|------|--------|--------|------------|
| Research blocks Content | Taif >3 days | +2-3 days delay | Saad starts structure while waiting |
| Standards blocks Content | Mohammad >3 days | +1-2 days delay | Saad uses standard mapping defaults |
| Review rejection | Score <85% | +3-5 days per cycle | Targeted revisions, not full rewrite |
| Format failures | Template errors | +1-2 days | Pre-validated templates, fallback formats |
| Owner delay | Khalid unavailable | +1-5 days | Pre-approved criteria, conditional delivery |

### 2.4 Bottleneck Resolution Framework

**Common Bottlenecks and Resolutions:**

| # | Bottleneck | Detection Signal | Impact Level | Resolution Strategy | Owner | SLA |
|---|-----------|-----------------|-------------|-------------------|-------|-----|
| B1 | Research delay | Taif >3 days on task | Medium | Simplify scope, provide cached references, parallel start content | Abdullah | 24h |
| B2 | Standards ambiguity | Mohammad requests clarification | Low | Escalate to Khalid for decision, use conservative interpretation | Ahmad | 8h |
| B3 | Content quality gap | Saad draft <70% quality | High | Additional research input, template reinforcement, targeted coaching | Abdullah | 48h |
| B4 | Review rejection loop | Score <85% twice | High | Abdullah reviews feedback, senior review of criteria, targeted fixes | Ahmad | 24h |
| B5 | Format rendering issues | Bee reports template errors | Medium | Fallback to clean markdown, manual adjustment | Abdullah | 12h |
| B6 | API rate limiting | Agent timeout/429 errors | Medium | Queue management, retry with backoff, batch processing | Abdullah | 4h |
| B7 | Client scope creep | New requirements mid-project | High | Document change request, re-estimate, Khalid approval | Ahmad | 24h |
| B8 | Knowledge gap | Agent lacks domain expertise | Medium | Knowledge enhancement session, reference material provision | Ahmad | 48h |
| B9 | Cross-agent conflict | Inconsistent outputs | Medium | Abdullah arbitrates, establish authoritative source | Abdullah | 12h |
| B10 | Owner unavailable | Khalid no response >48h | High | Pre-approved delegation, conditional proceed, queue decisions | Ahmad | 48h |

**Bottleneck Escalation Process:**
```
1. Detection: Monitor daily metrics for threshold violations
2. Assessment: Evaluate impact on timeline and quality
3. Notification: Alert Abdullah (operational) or Khalid (strategic)
4. Action Plan: Develop resolution within SLA
5. Execution: Implement resolution, monitor effectiveness
6. Documentation: Log bottleneck and resolution for pattern analysis
7. Prevention: Update processes to prevent recurrence
```

### 3.2 Version Control Protocol

**Semantic Versioning: MAJOR.MINOR.PATCH**
- **MAJOR** (1.0.0, 2.0.0): Significant structural changes, new sections, major rewrites
- **MINOR** (1.1.0, 1.2.0): Content updates, additions within existing structure
- **PATCH** (1.1.1, 1.1.2): Typo fixes, minor corrections, formatting adjustments

**Pre-release Versions:**
- v0.1.0 - Initial draft
- v0.2.0 - Incorporated research/standards input
- v0.3.0 - First complete draft
- v0.x-rc1 - Release candidate (post-review)
- v1.0.0 - First approved release

**Version History Entry Format:**
| Version | Date | Author | Reviewer | Changes | Approved By |
|---------|------|--------|----------|---------|-------------|

| 0.2.0 | [date] | Saad | - | Incorporated research + standards | - |

| 1.1.0 | [date] | Saad | Abdullah | Minor content update | Abdullah |
| 1.1.1 | [date] | Ahmad | - | Typo correction | Ahmad |

**Version Control Rules:**
1. Every change must have a version increment
2. No changes to approved documents without new version
3. Draft versions (0.x) can be freely updated
4. Minor versions (x.Y.z) require Abdullah approval
5. Major versions (X.0.0) require Khalid approval
6. All version changes logged in history table
7. Previous versions archived, never deleted

    2. Start Where You Are
    3. Progress Iteratively with Feedback
    4. Collaborate and Promote Visibility
    5. Think and Work Holistically
    6. Keep It Simple and Practical
    7. Optimize and Automate

**ITOM (IT Operations Management) Essentials:**
- ITOM covers the operational side of IT: monitoring, events, infrastructure
- **5 Core ITOM Processes**:
  1. **Event Management**: Detecting and responding to IT events (alerts, warnings, info)
  2. **Incident Management**: Restoring normal service after an unplanned interruption
  3. **Problem Management**: Finding and eliminating root causes of recurring incidents
  4. **Change Management**: Controlling changes to minimize risk and disruption
  5. **Configuration Management**: Maintaining the CMDB (Configuration Management Database)
- **ITOM.pdf** is our reference document, parsed for process-specific knowledge
- **Priority Matrix**: Impact × Urgency = Priority (P1-Critical through P5-Planning)

- **DevOps**: Integration of development and operations, CI/CD pipelines
- **Cloud Service Management**: Multi-cloud and hybrid operations
- **GitOps**: Infrastructure and operations managed through Git workflows

  4. Physical Security Monitoring (A.7.4)

  6. Information Deletion (A.8.10)
  7. Data Masking (A.8.11)
  8. Data Leakage Prevention (A.8.12)
  9. Monitoring Activities (A.8.16)
  10. Web Filtering (A.8.23)
  11. Secure Coding (A.8.28)
- Organizations had until **October 2025** to transition from 2013 to 2022

**ISO 20000 (IT Service Management):**
- International standard for ITSM, aligned with ITIL
- Certifiable standard (unlike ITIL which is a framework)

**COBIT 2019 (IT Governance):**

- Focus on stakeholder value creation

**Saudi-Specific Regulations (Critical for Saudi Clients):**

**Core Domain Knowledge:**

**SOP Document Structure (12 Mandatory Sections):**
Every SOP Saad writes must contain these 12 sections:

| # | Section | Pages | Purpose |
|---|---------|-------|---------|
| 1 | Cover Page | 1 | Title, version, approval signatures |
| 2 | Purpose & Scope | 1-2 | Why this SOP exists, what it covers |
| 3 | Definitions & Acronyms | 1-2 | Glossary of technical terms |
| 4 | Roles & Responsibilities | 2-3 | RACI matrix, role descriptions |
| 5 | Process Overview | 1-2 | High-level flow, objectives |
| 6 | Detailed Procedures | 5-10 | Step-by-step instructions with expected results |
| 7 | Process Flow Diagrams | 1-2 | Visual representation of the process |
| 8 | Escalation Procedures | 1-2 | When and how to escalate |
| 9 | KPIs & Metrics | 1-2 | Measurable performance indicators |
| 10 | Tools & Systems | 1-2 | Required technology and tools |
| 11 | Compliance & Standards | 1-2 | Standards mapping and references |
| 12 | Appendices | 2-4 | Forms, checklists, FAQs, templates |

**Technical Writing Quality Standards:**
- **Readability**: Flesch Reading Ease 60-70, Grade Level 8-10
- **Active Voice**: 90% active, maximum 10% passive
- **Sentence Length**: Average 15-20 words per sentence
- **RACI Matrix**: Every task has exactly ONE Accountable (A) person
- **Procedures**: Each step has an expected result documented

**RACI Matrix Rules:**
- **R (Responsible)**: Does the work (can be multiple)
- **A (Accountable)**: Ultimately answerable (must be ONE per task)
- **C (Consulted)**: Provides input before action
- **I (Informed)**: Notified after action
- Every row must have at least R and A
- A and R can be the same person but A is always exactly one

**How to Coordinate Saad:**

- If Saad needs additional input from Taif or Mohammad, coordinate quickly
- Saad delivers the **full SOP in Markdown** format to Faisal for review

**Quality Indicators for Saad's Output:**
- All 12 sections present and populated
- 15-30 pages in length
- RACI matrix complete with one "A" per row
- Procedures have numbered steps with expected results
- KPIs are SMART (Specific, Measurable, Achievable, Relevant, Time-bound)
- Standards compliance sections reference specific control numbers
- Readable, professional tone throughout

- **Concurrent Capacity**: 2 SOPs simultaneously

**Core Domain Knowledge:**

**Analytics Hierarchy (What SOPs Need):**
1. **Descriptive Analytics**: What happened? (Reports, dashboards, summaries)
2. **Diagnostic Analytics**: Why did it happen? (Root cause, drill-down, correlation)
3. **Predictive Analytics**: What will happen? (Forecasting, trend analysis, ML models)
4. **Prescriptive Analytics**: What should we do? (Optimization, recommendations)

Every SOP should include at minimum Descriptive and Diagnostic analytics.

**Power BI Ecosystem:**
- **Power BI Desktop**: Development tool (reports, models, DAX)
- **Power BI Service**: Cloud platform (publishing, sharing, collaboration)
- **Power BI Mobile**: Mobile access to dashboards
- **Power BI Report Server**: On-premises deployment
- **Power BI Embedded**: Integration into applications

**KPI Design Framework (SMART):**
Every KPI in an SOP must be:
- **S**pecific: Clear what is being measured (e.g., "Mean Time to Resolve Incidents")
- **M**easurable: Quantifiable (e.g., "in minutes")
- **A**chievable: Realistic target (e.g., "< 60 minutes for P1")
- **R**elevant: Aligned with business objectives
- **T**ime-bound: Measured over a defined period (e.g., "monthly average")

**ITSM-Specific KPIs Layla Designs:**

| Process | Key KPIs | Visual Type |
|---------|----------|------------|
| Incident Management | MTTR, MTTA, FCR%, SLA Compliance | KPI cards, line charts |
| Change Management | Change Success Rate, Emergency Change %, CAB Approval Time | Gauges, bar charts |
| Problem Management | Known Error Rate, MTTR for Problems, Recurring Incident % | Trend lines, Pareto |
| Asset Management | Asset Utilization, License Compliance, End-of-Life % | Heatmaps, stacked bars |
| Service Request | Fulfillment Time, Satisfaction Score, Request Volume | Funnels, tables |

**Dashboard Design Principles:**
- **5-Second Rule**: Key message visible within 5 seconds
- **F-Pattern**: Eyes scan left to right, top to bottom
- **Color Coding**: Red = Critical/Bad, Yellow = Warning, Green = Good/Target
- **Chart Selection**: Right chart for right data (never use pie for >5 categories)
- **Information Hierarchy**: KPI cards at top, details below, filters on side

**How to Coordinate Layla:**

- If client needs a **Power BI dashboard**, Layla provides complete design specs (DAX formulas, data model, visuals)

**Quality Indicators for Layla's Output:**
- All KPIs are SMART
- Dashboard design follows F-pattern and 5-second rule
- Color coding is consistent and accessible
- Chart types appropriate for data types
- DAX formulas syntactically correct
- Data model follows star schema best practices

    │   ├── "Access compliance" → Rakan + Mohammad via Abdullah
    │   └── "Client delivery" → Ahmad handles directly
    │
    ├── What's the priority?
    │   ├── Normal → Standard 18-24 day workflow
