## 1. TECHNICAL WRITING BEST PRACTICES

### 1.1 Core Principles
- **Clarity**: Use precise, unambiguous language
- **Conciseness**: Eliminate wordiness without sacrificing completeness
- **Accuracy**: Verify all technical details and procedures
- **Consistency**: Maintain uniform terminology, style, and structure
- **Completeness**: Cover all necessary information for task execution
- **Accessibility**: Write for diverse audiences and abilities
- **Actionability**: Ensure readers can perform tasks from documentation

### 1.2 The Seven C's of Technical Writing
1. **Clear**: Avoid jargon when possible; define when necessary
2. **Concise**: Use active voice; eliminate redundancy
3. **Concrete**: Provide specific examples and data
4. **Correct**: Verify technical accuracy and grammar
5. **Coherent**: Maintain logical flow and structure
6. **Complete**: Include all necessary information
7. **Courteous**: Respect reader's time and intelligence

### 1.3 Writing for Scanability
- Use descriptive headings (H1-H6 hierarchy)
- Break content into short paragraphs (3-5 sentences)
- Employ bullet points and numbered lists
- Highlight key terms using **bold** or *italic*
- Use tables for comparative information
- Include visual breaks (horizontal rules, spacing)

### 1.4 Active Voice vs Passive Voice
**Preferred (Active)**:
- "The administrator configures the firewall."
- "Click the Submit button to save changes."
- "The system generates a ticket ID automatically."

**Avoid (Passive)**:
- "The firewall is configured by the administrator."
- "The Submit button should be clicked to save changes."
- "A ticket ID is automatically generated by the system."

**Exception**: Passive voice acceptable when:
- Actor is unknown or irrelevant
- Emphasizing the action over the actor
- Maintaining consistency in procedure lists

## 2. SOP (STANDARD OPERATING PROCEDURE) WRITING

### 2.1 SOP Definition and Purpose
An SOP is a set of step-by-step instructions compiled by an organization to help workers carry out routine operations efficiently, consistently, and in compliance with standards.

**Core Purposes**:
- Ensure consistency and quality
- Facilitate training and onboarding
- Support compliance and auditing
- Reduce errors and variations
- Preserve organizational knowledge
- Enable business continuity

### 2.2 SOP Document Structure (Standard 15-30 Page Format)

#### Essential Components:
1. **Cover Page**
   - Document Title
   - Document ID/Reference Number
   - Version Number
   - Effective Date
   - Department/Process Owner
   - Approval Signatures

2. **Document Control Page**
   - Revision History
   - Distribution List
   - Document Location
   - Review Schedule

3. **Table of Contents**
   - Automatically generated
   - Include page numbers
   - 3-level depth minimum

4. **1.0 Purpose**
   - Why this SOP exists (2-3 paragraphs)
   - Business objectives
   - Expected outcomes

5. **2.0 Scope**
   - What is covered
   - What is NOT covered
   - Boundaries and limitations
   - Applicable departments/roles

6. **3.0 Definitions and Acronyms**
   - Alphabetical glossary
   - Industry-specific terms
   - System/tool names

7. **4.0 Roles and Responsibilities (RACI)**
   - Detailed RACI matrix
   - Role descriptions
   - Authority levels

8. **5.0 Process Overview**
   - High-level flowchart (described in text)
   - Process inputs and outputs
   - Key decision points
   - Integration with other processes

9. **6.0 Detailed Procedures**
   - Step-by-step instructions
   - Substeps and decision trees
   - Screenshots placeholders
   - Expected results after each step

10. **7.0 Escalation Procedures**
    - When to escalate
    - Escalation paths
    - Contact information
    - SLA/timeframes

11. **8.0 Quality Standards and KPIs**
    - Success metrics
    - Quality checkpoints
    - Compliance requirements
    - Performance targets

12. **9.0 Tools and Systems**
    - Required software/hardware
    - Access requirements
    - Configuration notes
    - Integrations

13. **10.0 References and Related Documents**
    - Related SOPs
    - External standards (ITIL, ISO, COBIT)
    - Regulatory requirements
    - Training materials

14. **11.0 Appendices**
    - Forms and templates
    - Checklists
    - Troubleshooting guides
    - FAQs

### 2.3 SOP Formatting Standards

#### Numbering System:
- **Hierarchical Decimal**: 1.0, 1.1, 1.1.1, 1.1.2, 1.2, 2.0
- **Procedures**: Use numbered lists (1, 2, 3...)
- **Sub-procedures**: Use lettered lists (a, b, c...)
- **Notes/Tips**: Use bullet points (•)

#### Typography:
- **Headings**: Bold, Title Case
- **Body Text**: 11-12pt, left-aligned
- **Code/System Text**: `Monospace font`
- **Emphasis**: **Bold** for critical information, *italic* for notes
- **Links**: [Descriptive text](URL)

#### Page Layout:
- **Margins**: 1 inch all sides
- **Line Spacing**: 1.15-1.5 for body text
- **Header**: Document title, version, page number
- **Footer**: Confidentiality statement, effective date

## 3. PROCESS DOCUMENTATION METHODOLOGIES

### 3.1 Process Mapping Techniques

#### Narrative Description:
"The Incident Management process begins when a user reports an issue via phone, email, or self-service portal. The Service Desk agent logs the incident in the ticketing system, categorizes it, and assigns an initial priority based on impact and urgency..."

#### Procedural Steps:
```
1. Receive incident notification
2. Log incident details in system
   a. Record user information
   b. Document symptoms
   c. Assign category
3. Classify priority (P1-P4)
4. Route to appropriate resolver group
```

#### Decision Trees (Text Format):
```
IF Priority = P1 (Critical)
  THEN Notify Major Incident Manager immediately
  AND Assemble crisis team
ELSE IF Priority = P2 (High)
  THEN Assign to Level 2 support
  AND Set response time = 4 hours
ELSE
  THEN Assign to Level 1 support queue
  AND Follow standard resolution process
ENDIF
```

## 4. RACI MATRIX CREATION AND MANAGEMENT

### 4.1 RACI Framework Explained
- **R - Responsible**: Performs the work
- **A - Accountable**: Ultimately answerable; approves work (only ONE per task)
- **C - Consulted**: Provides input; two-way communication
- **I - Informed**: Kept updated; one-way communication

### 4.2 RACI Matrix Template

```markdown
| Activity/Task                          | Service Desk | Team Lead | IT Manager | Change Manager | End User |
|----------------------------------------|--------------|-----------|------------|----------------|----------|
| Log Incident                           | R            | I         | I          | -              | C        |
| Categorize and Prioritize             | R            | C         | I          | -              | I        |
| Assign to Resolver Group              | R            | A         | I          | -              | I        |
| Investigate and Diagnose              | R/C          | A         | I          | -              | C        |
| Implement Resolution                   | R            | A         | C          | C*             | I        |
| Verify Resolution                      | R            | A         | I          | -              | C        |
| Close Incident                         | R            | A         | I          | -              | I        |
| Review Major Incidents                 | C            | C         | A          | C              | -        |

*If change required
```

### 4.3 RACI Best Practices
- **One Accountable per task**: Avoid diffusion of responsibility
- **Not everyone needs a role**: Use "-" for non-involved parties
- **Clear role definitions**: Define each role in a separate section
- **Review with stakeholders**: Validate accuracy and acceptance
- **Update regularly**: Reflect organizational changes
- **Link to job descriptions**: Ensure alignment with formal roles

### 4.4 Common RACI Mistakes to Avoid
- Multiple Accountable parties (creates confusion)
- Too many Consulted (slows process)
- Missing Responsible (work doesn't get done)
- Everyone Informed (information overload)
- Vague activity descriptions

### 4.5 RACI Variations
- **RACI-VS**: Add Verifies and Signs off
- **RASCI**: Add Supportive role
- **DACI**: Driver, Approver, Contributor, Informed (alternative framework)
- **RAPID**: Recommend, Agree, Perform, Input, Decide (Bain & Company model)

## 5. PROCEDURE WRITING STANDARDS

### 5.1 Step-by-Step Instructions Format

#### Standard Procedure Format:
```markdown
### 6.3 Incident Logging Procedure

**Objective**: Create a complete and accurate incident record in the ticketing system.

**Prerequisites**:
- Access to ServiceNow Incident Management module
- Valid Service Desk agent credentials
- User contact information available

**Steps**:
1. Open ServiceNow and navigate to **Incident > Create New**.
   - Expected Result: Blank incident form displays

2. Complete the **Caller Information** section:
   a. Enter caller name in the **Caller** field
   b. Verify and update phone number
   c. Confirm email address
   - Expected Result: Caller record auto-populates from CMDB

3. Document the incident in the **Short Description** field:
   - Use format: "[System/Service] - [Issue Summary]"
   - Example: "Email - Unable to send messages with attachments"
   - Expected Result: Description is clear and searchable

4. Enter detailed symptoms in the **Description** field:
   - Include error messages (exact text)
   - Document steps user took before issue occurred
   - Note when issue started
   - Expected Result: Complete technical context captured

5. Select appropriate **Category** from dropdown:
   - Software > Email
   - Hardware > Desktop
   - Network > Connectivity
   - Expected Result: Category determines routing

6. Set **Impact** level:
   - 1-High: Multiple users/critical service affected
   - 2-Medium: Single user/non-critical service
   - 3-Low: Minimal business impact
   - Expected Result: Impact is documented

7. Set **Urgency** level:
   - 1-High: Work is stopped
   - 2-Medium: Work is slowed
   - 3-Low: Minor inconvenience
   - Expected Result: Urgency is documented

8. **Priority** auto-calculates based on Impact and Urgency matrix.
   - Verify Priority is correct (P1-P5)
   - Expected Result: Priority drives SLA

9. Click **Submit** to create the incident.
   - Expected Result: Incident number generated (INC + 7 digits)

10. Communicate incident number to the caller.
    - Use phrase: "Your incident number is INC0001234 for reference."
    - Expected Result: Caller can track incident status

**Post-Procedure**:
- Incident appears in Service Desk queue
- SLA timer starts based on Priority
- Automated notification sent to caller

**Troubleshooting**:
- If caller not found: Create new user record first
- If category unclear: Consult Category Guide (Appendix B)
- If system slow: Log performance issue separately
```

### 5.2 Decision Tree Format
```markdown
### 5.4 Priority Assignment Decision Tree

START: New incident logged

QUESTION 1: How many users are affected?
  → Multiple users: GO TO QUESTION 2a
  → Single user: GO TO QUESTION 2b

QUESTION 2a: Is this a critical business service?
  → Yes: SET Impact = 1-High, GO TO QUESTION 3
  → No: SET Impact = 2-Medium, GO TO QUESTION 3

QUESTION 2b: Is the user a VIP or executive?
  → Yes: SET Impact = 2-Medium, GO TO QUESTION 3
  → No: SET Impact = 3-Low, GO TO QUESTION 3

QUESTION 3: Is work completely stopped?
  → Yes: SET Urgency = 1-High
  → No: GO TO QUESTION 4

QUESTION 4: Is work significantly slowed?
  → Yes: SET Urgency = 2-Medium
  → No: SET Urgency = 3-Low

FINAL STEP: Calculate Priority
  Impact 1 + Urgency 1 = Priority 1 (Critical)
  Impact 1 + Urgency 2 = Priority 2 (High)
  Impact 2 + Urgency 2 = Priority 3 (Medium)
  All others = Priority 4 or 5 (Low)

END: Priority assigned, proceed to routing
```

## 7. WRITING STYLE GUIDES

### 7.1 Microsoft Manual of Style (Technical Documentation)
Key principles:
- Use simple words and short sentences
- Write in second person for procedures ("you")
- Use present tense
- Avoid jargon; explain technical terms
- Use parallelism in lists
- Gender-neutral language

**Example**:
❌ "The user should click on the button which will then navigate him to the dashboard."
✅ "Click the button to go to the dashboard."

### 7.2 Chicago Manual of Style (Academic/Formal)
When to use:
- White papers
- Research reports
- Academic IT publications

Key principles:
- More formal tone
- Third person acceptable
- Footnotes and citations
- Serial comma required

### 7.3 Technical Writing Style Guide (Custom for IT SOPs)

#### Voice and Tone:
- **Professional** but approachable
- **Authoritative** but not condescending
- **Clear** but not overly simplistic
- **Consistent** throughout document

#### Pronouns:
- **Use "you"** when addressing user: "You can reset the password..."
- **Use "we"** for organizational actions: "We recommend quarterly reviews..."
- **Avoid "they"** when referring to user; use "the user" or role name

#### Tense:
- **Present tense** for procedures: "Click the button. The system displays..."
- **Future tense** for consequences: "This will prevent data loss."
- **Past tense** for context: "This issue occurred in Q3 2025."

#### Numbers:
- **Spell out**: One through nine
- **Use numerals**: 10 and above
- **Exception**: Always use numerals in procedures, measurements, versions
  - "Step 1", "Version 2.5", "Wait 5 seconds"

#### Capitalization:
- **Job Titles**: Capitalize when referring to specific person
  - "Contact the IT Manager" (specific role)
  - "The incident manager logs the ticket" (generic role)
- **System Names**: Capitalize as branded
  - ServiceNow, Microsoft 365, Cisco Webex
- **UI Elements**: Match system capitalization
  - "Click the Submit button" (if system shows "Submit")

#### Lists:
- **Parallel structure**: All items same grammatical form
  - ✅ "Configure, Test, Deploy"
  - ❌ "Configure, Testing, To Deploy"
- **Punctuation**:
  - No periods if items are fragments
  - Periods if items are complete sentences
- **Introduction**: Complete sentence ending with colon

## 8. PLAIN LANGUAGE PRINCIPLES

### 8.1 Core Plain Language Rules
1. **Use common words**: "use" not "utilize", "help" not "facilitate"
2. **Short sentences**: 20 words or fewer average
3. **Active voice**: "The agent closes the ticket" not "The ticket is closed"
4. **Direct address**: "You" not "the user"
5. **Concrete examples**: "Wait 30 seconds" not "Wait a short time"

### 8.2 Complexity Metrics
- **Flesch-Kincaid Grade Level**: Target 8-10 for general IT documentation
- **Flesch Reading Ease**: Target 60-70 (plain English)
- **Average sentence length**: 15-20 words
- **Percentage passive voice**: Under 10%

### 8.3 Jargon Management
**Three-tier approach**:
1. **Avoid**: Use plain language alternative
   - ❌ "leverage" → ✅ "use"
   - ❌ "ascertain" → ✅ "find out"

2. **Define**: Explain on first use
   - "The Configuration Item (CI) is the component being managed."

3. **Accept**: Common industry terms
   - SLA, ITIL, CMDB (but still define in glossary)

### 8.4 Plain Language Checklist
- [ ] Average sentence under 20 words?
- [ ] Active voice used 80%+ of time?
- [ ] Jargon defined or eliminated?
- [ ] Second person ("you") used in procedures?
- [ ] Concrete examples provided?
- [ ] Short paragraphs (3-5 sentences)?
- [ ] Clear headings and subheadings?
- [ ] Lists used for multiple items?

## 9. CONTENT ORGANIZATION PATTERNS

### 9.1 Inverted Pyramid Structure
Most important information first:
```
[Critical Information - What/When/Who]
    ↓
[Important Details - How/Why]
    ↓
[Background/Context]
    ↓
[Supporting Information]
    ↓
[References]
```

### 9.2 Modular Content Strategy
- **Content Blocks**: Reusable sections (e.g., "Prerequisites", "Troubleshooting")
- **Single-Source**: Write once, publish many formats
- **Variables**: Use placeholders for system-specific terms
- **Conditional Text**: Include/exclude based on audience

### 9.3 Progressive Disclosure
Layer information by audience need:
- **Level 1**: Quick Start (5 minutes)
- **Level 2**: Standard Procedure (complete steps)
- **Level 3**: Advanced Options (power users)
- **Level 4**: Technical Details (system admins)
- **Level 5**: Architecture/Design (engineers)

## 11. AUDIENCE ANALYSIS AND ADAPTATION

### 11.1 IT Audience Personas

#### Persona 1: Service Desk Tier 1
- **Technical Level**: Basic IT literacy
- **Time Available**: 2-5 minutes per document
- **Need**: Step-by-step instructions, no assumptions
- **Format Preference**: Checklists, visual aids, quick reference

#### Persona 2: System Administrator
- **Technical Level**: Advanced
- **Time Available**: 10-30 minutes
- **Need**: Technical details, configuration parameters
- **Format Preference**: Technical specs, command references

#### Persona 3: IT Manager
- **Technical Level**: Moderate
- **Time Available**: 5-10 minutes
- **Need**: Process overview, KPIs, compliance
- **Format Preference**: Executive summaries, dashboards, reports

#### Persona 4: End User
- **Technical Level**: Varies (low to moderate)
- **Time Available**: 1-3 minutes
- **Need**: Self-service resolution, simple language
- **Format Preference**: FAQs, screenshots, short videos

### 11.2 Adaptation Strategies
- **Service Desk**: Use numbered steps, include expected results, provide troubleshooting
- **Technical Teams**: Include architecture diagrams, API details, advanced options
- **Management**: Lead with business impact, include metrics, summarize key points
- **End Users**: Use analogies, avoid jargon, provide examples

### 11.3 Multi-Audience Documents
When single document serves multiple audiences:
1. **Layered Approach**: Executive summary → Process overview → Detailed procedures
2. **Role-Based Sections**: Label sections by role
3. **Visual Indicators**: Icons or tags for audience (e.g., [Tech], [Mgmt], [User])
4. **Separate Appendices**: Technical details in appendix for advanced users

## 18. LOCALIZATION AND INTERNATIONALIZATION CONSIDERATIONS

### 18.1 Writing for Translation
Even if not immediately translating:

#### Avoid Idioms and Colloquialisms:
❌ "Kick off the incident process"
✅ "Start the incident process"

❌ "This is a no-brainer"
✅ "This is clearly the best option"

#### Use Simple Sentence Structure:
❌ "Having logged the incident, the agent, who should be familiar with the categorization scheme, assigns a priority."
✅ "After logging the incident, the agent assigns a priority. The agent should be familiar with the categorization scheme."

#### Avoid Culture-Specific References:
❌ "The system is down more often than a quarterback on Sunday"
✅ "The system has frequent outages"

#### Date and Time Formats:
- Use ISO 8601: `2026-01-19` or `2026-01-19T14:30:00Z`
- Spell out months to avoid confusion: `19 January 2026`
- Specify time zones: `14:30 UTC` or `14:30 EST`

#### Numbers and Measurements:
- Use international standards (metric)
- Provide conversions if US units used
- Use spaces for thousands: `10 000` not `10,000` (or use commas per locale)

### 18.2 Internationalization (i18n) Preparation
- **Separate text from code**: Use variables for tool names, system paths
- **Leave space for expansion**: Translated text can be 30% longer
- **Avoid concatenation**: "You have " + count + " incidents" may not work in all languages
- **Support right-to-left languages**: Structure allows RTL if needed

### 18.3 Localization (l10n) Considerations
When localizing SOPs:
- **Legal/Compliance**: May vary by country
- **Standards**: ISO vs. ANSI, regional regulations
- **Tools**: Software versions, availability may differ
- **Contact Information**: Local support numbers, emails
- **Examples**: Use locale-appropriate examples

### 3.1 Key Terms

**Change**: The addition, modification, or removal of anything that could have an effect on IT services. The scope includes all IT services, configuration items, processes, documentation, etc.

**Configuration Item (CI)**: Any component that needs to be managed in order to deliver an IT service. Examples: hardware, software, documentation, personnel, facilities.

**Escalation**: The transfer of an incident, problem, or change to a higher level of technical expertise or management authority.

**Incident**: An unplanned interruption to an IT service or reduction in the quality of an IT service. Example: Email service unavailable, printer not working.

**Priority**: A category assigned to incidents, problems, or changes to define the order in which they should be addressed. Priority is typically calculated from Impact and Urgency.

**RACI Matrix**: A responsibility assignment matrix that defines Responsible, Accountable, Consulted, and Informed roles for each task in a process.

**Service Level Agreement (SLA)**: A formal agreement between a service provider and customer that documents service level targets and responsibilities.
